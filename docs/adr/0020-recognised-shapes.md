# CSS translates to a visible XML pattern, and the compiler recognises shapes of it and runs them by dedicated methods

Some queries are orders of magnitude slower than queries that look no harder. On a 2,032-element page `li a` takes 4 ms and `li:first-child a` 30 ms, and `tr:nth-child(2n+1 of .a)` over 1,000 siblings takes 6.6 s, because its translation is a `Count` inside a `Condition` that `ReplaceList` tests on every split of the list. No value said how a query runs. The compiler gave a compiled query that said what it means, and each runner decided at run time how to run it. Speed-ups went into two places, neither written down as a guarantee: the translator, which writes a faster equivalent pattern (ADR 0017, positions moved along a `+` run), and the list matcher, which recognised the exact pattern shape that the select-rule builder wrote 60 lines away (`{___, s, ___}`, ADR 0016's Consequences). Settled in the architecture review of 2026-10-06 and its spec, `.scratch/compiled-query-plan/spec.md`.

## Decision

### The pipeline

A query goes one way: a CSS selector translates to a visible, WL-native XML pattern, with `Condition`, `PatternTest` or `Except` where it needs them, and the compiler compiles that pattern into a compiled query. The translator emits no private head, and there is no path from CSS to a compiled query that skips the XML pattern. A CSS-side optimisation is a choice of which pattern to emit, in a shape the compiler recognises.

### Recognised shapes

The compiler may recognise a **shape** of XML pattern and run it by a dedicated method, with the same results, in content, order, count and bindings, as WL's matcher gives on the pattern as written. A recognised shape is a performance guarantee: it is listed below, each with a performance test in `Tests/Performance` whose time limit fails `make test` when the shape stops being recognised. A pattern written in a shape that is not recognised gives the same answer, only more slowly. Recognition is never a condition of correctness.

The decision is made once, by `compileQuery`, from the query alone and never from the tree, and is recorded in the compiled query: each list stage carries its method, a recognised shape with its parameters or the general matcher with its rule. The runners read the method and do not inspect the pattern.

A private switch, `$recogniseShapes`, turns recognition off for an evaluation (`Block[{$recogniseShapes = False}, …]`), so that every list stage runs on the general matcher. It is for tests and maintainers, to check a recognised method against WL's matcher on the same input (`Tests/Unit/RecognisedShapes.wlt`). The compiled query records whether recognition was on, and the `XMLMatchQ` operator-form cache keys on the switch.

### Compounds are intersected on the CSS side

The translator intersects the simple selectors of a compound in its own branch form, before it projects the result to an `XMLPattern`. An intersection may need a disjunction, such as several tags or two constraints on one key, that a single `KeyValuePattern` cannot hold, so it cannot be done after the projection.

### Context entries are compiled once

A context combinator entry of a list stage (ADR 0016) is compiled once, with the query, as a chain of its own in the compiled query's `"ContextEntries"`, with its stages, tuple test and two-step match built and any list stage in it given its method. A run tests a child against it from that child's site, at most once per child, and builds nothing for it. This is a property of the compiled query, not a recognised shape. A list stage with context entries is shape 6 when its entries are ordered entries, and otherwise runs on the general matcher, at the general matcher's cost. `Child["body", {___, Child["div", "p"], ___, "div.c3", ___}]` over 3,000 siblings took about 39 s on the general matcher, because `ReplaceList` enumerates every split of the list that places the two entries, about as slowly with the context entry's test replaced by `True`; as shape 6 it takes about 78 ms (`perf-shape-ordered-context-entry-3000-siblings`). With the two entries adjacent, `{___, Child["div", "p"], "div.c3", ___}`, the general matcher tries one split per `div.c3` and took about 70 ms (`perf-context-entry-3000-siblings`); that list is shape 6 too, at about the same time, most of it in the context entry.

### Rule bodies bind from the selected child

In every recognised shape only the selected entry can name anything: a list with a name on another entry, or on the list itself, is not recognised. So in the tuple of elements that a rule body, a `Condition` in it and a `Condition` on a combinator are matched against (ADR 0014), a list stage run as a recognised shape is replaced by its selected entry, matched against the selected child, and the list is not matched again. The method has already checked the child's place and its context entries. The selected entry's own names, `Condition`s, tests and two-step match bind as at any element stage, and the names it shares with other stages are one value, as before. A list stage on the general matcher keeps the whole list in the tuple, matched on WL's matcher, since another entry, a sequence entry or the list itself may bind a name there. The results are the same, in content, order and bindings, because with only the selected entry named the list can bind its names in one way only, so a body `Condition` that rejects one match has no other to try at that stage.

### Depends on WL's matcher

Some recognised shapes exist because WL's own matcher is slow on them, reported as bug(479398): `{___, z | w, ___}` takes time quadratic in the list length where `{___, z, ___}` is linear, and each further `___, z | w` slot raises the degree by about one. `Tests/Performance/WLMatcher.wlt` holds canaries for it, test IDs `wl-matcher-479398-…`. They test WL, not the paclet, and pass while the matcher is slow. The one-slot canary guards shape 1, the two-slot canary shape 6 (ordered entries), and the two counted-form canaries shapes 4 and 5 (counted positions). One of these, on a list where the match exists, is slow even with a literal `p`, beyond what the bug reports, so it may keep passing after the bug is fixed. When a canary fails, measure the shapes it names against the general matcher (`$recogniseShapes = False`) on that WL version, and decide whether to keep them or to let WL's matcher run them from that `$VersionNumber` on. A failure is not a paclet regression.

## Consequences

The `{___, s, ___}` shape is recognised in one place, the compiler, from the list stage as compiled, and the list matcher no longer re-matches the select rule's shape at run time. Recognition still reads the compiled list's entries, so a change to how list stages are compiled must keep the recognisers in step. Behaviour and timing are unchanged: the performance tests measured the same before and after.

Shapes 2 and 3 make a position among all children cost about what the selector without it does: on the 2,032-element `Tests/assets/wolfram-language.html`, `li:first-child a` and `li:nth-child(2n+1)` went from about 28 ms to 9 ms, against 4 ms for `li a`. Most of what remains is visiting every element as a possible parent, since the translation's parent stage, `XMLDocument[] | XMLPattern[_]`, matches every element. A fixed position such as `:nth-last-child(3)` was already fast on one long list, since WL's matcher places a fixed-length prefix or suffix at once, so its performance test would not tell the shape apart; the tests use `2n+1`, which the general matcher tries at every split.

The arithmetic sets of lengths, and which lengths up to a bound they hold, are decided in one place (`lengths`, `lengthsUpTo`), for the counted positions to reuse. Shape 1 also passes over a parent with no child that `C` matches, which took `Child[XMLDocument[] | XMLPattern[_], {___, XMLPattern["li"], ___}]` on that page from about 29 ms to 9 ms.

Shapes 4 and 5 make a position among the siblings that match a pattern linear in the number of siblings. Before them, the translator wrote such a position as `{g___, c : C, ___} /; Count[{g}, S] + 1 …`, which `ReplaceList` tests on every split of the list, and it now writes the plain entries of shape 4 or 5 (ADR 0017), whose `S` is an ordinary entry the compiler compiles. The two land together: on WL's own matcher the plain entries are slower still than `Count`, as `Except[t] ...` beside a non-literal `t` backtracks (`tr:nth-child(2n+1 of .a)` and `li:nth-last-of-type(2)` below did not finish in 60 s with recognition off). Measured on a 2026 laptop, recognition on, against the `Count` form before: `tr:nth-child(2n+1 of .a)` over 1,000 rows 12 ms against 8.3 s; `li:nth-last-of-type(2)` over 5,000 siblings 18 ms against 440 ms; on `Tests/assets/wolfram-language.html`, `li:nth-of-type(2n+1) a` 13 ms against 35 ms, `li:last-of-type` 10 ms against 28 ms, and `li:nth-child(2 of :has(a))` 101 ms against 932 ms, where `S` is tested whole with `XMLMatchQ` once per child. Shapes 4 and 5 reuse shape 2's sets of lengths and their membership (`lengthsOf`, `lengthsUpTo`): a unit is read as one `_`, and the count of children that match `t` takes the place of the index.

Some counted positions stay on the general matcher, as a condition on the list with a `Count`: one in a run of compounds joined by `+` or `~` (other than the first or last of its kind on the run's first or last compound, which the translator already wrote with plain entries), whose list has several XML-pattern entries, two positions on one side of one compound, and `-of-type` on a compound with no type, which counts the siblings with the element's own tag, not a pattern. So does a counted position whose `t` binds a name, as in `{Except[t] ..., PatternSequence[x : t, Except[t] ...] ..., C, ___}`, where WL gives the name one value across the repeats, which counting would not respect.

Shape 6 makes a list stage of ordered entries linear in the number of siblings. On the general matcher, each `___` between two entries multiplies the splits `ReplaceList` enumerates by about the number of children, so with two entries its time and memory grow about as the cube of the number of siblings (bug(479398) reports the same growth in `MatchQ`). Measured on a 2026 laptop, recognition on, against the general matcher: `Child["body", {___, Child["div", "p"], ___, "div.c3", ___}]` 10 ms against 37 ms at 200 siblings, 28 ms against 1.6 s at 1,000, and 78 ms against about 39 s at 3,000; `{___, XMLPattern["h2"], ___, XMLPattern["p"], ___}` 10 ms at 5,000 siblings, against 1.2 s at 1,000 and 9.9 s at 2,000 on the general matcher, which was not run at 5,000, as its memory would not allow. The method selects the children. As first built, it did not bind names: a query with a rule body, or with a `Condition` on a combinator that spans the list stage, matched the whole list again on WL's matcher for each selected child, to bind the names (ADR 0014). That cost about the number of siblings per result for every shape, so a body over 1,000 siblings with a result at every third added about 0.6 s for shape 1 and 1.1 s for shape 2, and with a `___` between two entries before the selected one it also tried their placements: `{___, XMLPattern["h2"], ___, c : XMLPattern["p"], ___} :> c[[1]]` took 0.26 s at 200 siblings and more than 60 s at 1,000. A recognised list stage was then made to bind the names from the selected child (see "Rule bodies bind from the selected child").

With that, a rule body costs about what the query without one does. Measured on a 2026 laptop, over a section of h2, p and div in turn, matching the list again against binding from the selected child: `{___, XMLPattern["h2"], ___, c : XMLPattern["p"], ___} :> c[[1]]` 0.26 s → 3 ms at 200 siblings, more than 60 s → 5 ms at 1,000, and 22 ms at 5,000 (20 ms without the body); `{_, PatternSequence[_, _, _]..., c : XMLPattern["p"], ___} :> c[[1]]` (shape 2) 1.1 s → 4 ms at 1,000 and 23 ms at 5,000; `{___, c : XMLPattern["p"], ___} :> c[[1]]` (shape 1) 0.63 s → 4 ms at 1,000. Performance tests: `perf-shape-ordered-body-5000-siblings`, `perf-shape-from-start-body-5000-siblings`, each bounded in memory as well as time, since a regression to matching the list again would grow about as the cube of the number of siblings.
